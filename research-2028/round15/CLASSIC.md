# A code-based SG-DIFRA profile with a studied security foundation

This configuration combines Classic McEliece with an actual instance of the Round 14 SG-DIFRA KEM. Both components use codes. The first uses a private binary Goppa decoder. The second uses a ternary differential mask and disjoint secret checks. Key generation and encapsulation draw their randomness independently. Both secrets and both ciphertexts enter the final key derivation. The package uses the cached public-context mode of the [parallel combiner](COMBINER.md).

All three produce a 32-byte shared key. Each public key includes 532 bytes from the ternary component. Each private key includes its 64-byte native private representation and 32 bytes to bind the public context. Each ciphertext contains 195 additional bytes from SG-DIFRA. The layouts use the stated Classic McEliece parameter sets without plaintext confirmation. [Classic McEliece specification](https://classic.mceliece.org/mceliece-spec-20221023.pdf)

**What is proved.** Both component algorithms have perfect honest agreement in the mathematical model. In the single-recipient CCA game, assume Classic McEliece has IND-CCA security for its actual ciphertexts and the combiner satisfies the stated split-key pseudorandomness bound. Then the combined algorithm has conditional IND-CCA security, hence IND-CPA security. This implication holds even if the small SG-DIFRA component supplies no secrecy. The hash premise has a quantum random-oracle formulation. The [combiner theorem](COMBINER.md) specifies the losses, the classical decapsulation interface and the error terms. Classic McEliece's own proof has assumptions on one-way decoding and hashes. Its security guide distinguishes the model transform, concrete key generation and the choice of hash function. [Classic McEliece security guide, §§2, 5.3–5.5](https://classic.mceliece.org/mceliece-security-20221023.pdf)

**What this establishes about SG-DIFRA.** There is also an explicit, witness-preserving [binary-to-ternary differential representation](BINARY_BRIDGE.md) of the actual component's decoding problem. A matching generated cubic collision contains exactly the weight-constrained binary error vector. This explains the mathematical connection without attributing the security of Goppa decoding to a newly established, independent ternary assumption. The provider uses its own private decoder and transmits its own compact binary representation. The expanded cubic proof object never appears on the wire.

**Provider and validation.** The [Linux adapter](classic_kem.py) calls the native keypair, encapsulation and decapsulation operations provided by the system's libmceliece.so.1. The library supplies Classic McEliece arithmetic and randomness. Key and ciphertext lengths are checked before calling the fixed-size C API. The three chosen variants have byte-aligned ciphertext formats; their provider uses implicit rejection on an invalid fixed-width challenge. The research wire rejects a wrong total length or explicit native-component failure. The reference has Python-managed secret bytes and variable-time SG-DIFRA operations. Side-channel resistance and an implementation audit of the composite protocol remain open. [Debian library package](https://packages.debian.org/trixie/libmceliece1) · [Official library API](https://lib.mceliece.org/api.html)

The [integration tests](test_classic_kem.py) run complete full-size exchanges in all three profiles. A [separate interoperability check](test_binary_bridge.py) supplies a known binary error, calculates its syndrome independently from a fresh real public key, and compares the private library's decapsulation with the specified SHAKE256 output. The full-size check evaluates the compact relation directly. Small inputs test the compiled cubic equations exhaustively. Interoperability verifies agreed outputs and wire layout. It does not give a numerical lower bound on computational work.

A separate interoperability run generated public keys in libmceliece and encapsulated using the independently packaged pqcrypto 1.0.0 implementation, then reversed the providers. Both directions agreed at each of the three parameter sets. The Python package is not required for any published entry point or test.
